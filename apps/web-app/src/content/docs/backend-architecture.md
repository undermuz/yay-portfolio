# Backend: микросервисы на NestJS

Платформа доставки еды. Клиенты ходят только в HTTP-gateway своей роли. Gateway не хранит доменное состояние: он проверяет доступ и проксирует запрос в нужный микросервис через RabbitMQ. Доменная логика живёт в core-сервисах, аутентификация — в отдельных auth-сервисах.

## Стек

- **NestJS 11**, монорепозиторий, сборка webpack
- **TypeORM + MySQL** — одна primary-база, миграции в общей библиотеке
- **RabbitMQ** — RPC между gateway и микросервисами и системные события
- **Redis** — кэш и очереди фоновых задач (Bull)
- **JWT** — отдельные модули и секреты на роль: клиент, вендор, курьер, админка
- **S3-совместимое хранилище** файлов
- **Vitest + Testcontainers** — e2e поднимает MySQL, RabbitMQ и Redis
- Контракты HTTP API вынесены в отдельный пакет и шарятся с клиентами

## Структура

```text
backend-app/
├── apps/
│   ├── gateways/   customer, vendor, courier, control-panel, payments
│   ├── auth/       customer, vendor, courier, control
│   ├── core/       customer, vendor, courier, control, orders,
│   │               delivery, payments, watchdog
│   └── cli/
└── libs/
    ├── primary-db          TypeORM, entities, migrations
    ├── primary-rmq         брокер, паттерны сообщений, системные события
    ├── primary-redis       cache + Bull
    ├── primary-aws-s3      файлы
    ├── contracts           HTTP-контракты API
    ├── auth                guards и JWT по ролям
    ├── flows               сценарии заказа и GPS курьера
    └── base-transactions   кошельки и платежные side-effects
```

Около 20 разворачиваемых приложений: 5 gateway, 4 auth, 8 core и служебные cli.

## Как идёт запрос

```text
Web / Mobile
    → HTTP Gateway (customer | vendor | courier | control | payments)
        → RabbitMQ, очередь на токен сервиса
            → Auth MS или Core MS
                → MySQL / Redis / S3
```

1. Клиент вызывает REST своего gateway.
2. Gateway применяет guard, throttle и валидацию.
3. Контроллер наследует прокси и отправляет сообщение по именованному паттерну.
4. Core-обработчик принимает `@MessagePattern`, работает с репозиторием TypeORM и отвечает в ту же очередь.
5. Системные реакции (таймеры заказов, watchdog) идут отдельными событиями, а не синхронным RPC.

## Правила слоёв

- Клиент не ходит в core напрямую. Точка входа — gateway.
- Gateway не дублирует персистентность core.
- Auth и core разведены по приложениям и очередям.
- Схема базы одна, миграции централизованы.
- Публичный контракт ответа фиксируется в пакете контрактов, а не собирается «на глаз» в контроллере.

## Решения, которые держат систему

- **Токен очереди.** Один DI-токен мапится на очередь из окружения. Новый gateway подключается к брокеру без ручного копирования строк подключения.
- **Gateway как BFF.** На одном gateway несколько клиентов брокера: core, auth, orders, payments. Монолита при этом нет.
- **Contract-first.** Типы запросов и ответов живут в общем пакете, фронт и gateway смотрят в один контракт.
- **Сценарий заказа версионируется.** Flow заказа — отдельная библиотека с действиями, событиями и ошибками, а не россыпь if в контроллере.
- **Watchdog.** Отдельный сервис слушает системные события и следит за SLA заказа: таймауты и отложенные реакции.
- **Именованные лимиты.** Throttle делится по IP, email и телефону. У auth-эндпоинтов нет одного общего лимита «на всё».
- **E2E близко к продовой топологии.** Тест поднимает набор Nest-приложений и бьёт в них HTTP, а зависимости — реальные контейнеры.

## Данные и платежи

Сущности и миграции лежат в `primary-db`. Core-сервисы берут репозитории через `@InjectRepository` и общие CRUD-сервисы. Кошельки и платежи проходят через библиотеку транзакций: побочные эффекты публикуются локальной шиной уже внутри транзакции, а не размазаны по контроллерам.
